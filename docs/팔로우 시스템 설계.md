# 팔로우 시스템 설계

## 문서 목적과 범위

- 이 문서는 사용자 간 팔로우 관계, 팔로워·팔로잉 수 조회와 동시 팔로우 요청 처리 방식을 설명한다.
- 인증 상태는 기존 서버 세션에서 가져오며, Redis 공유 세션의 내부 구조는 `서버 세션과 Redis 중앙 저장소 설계.md`에서 관리한다.

## 1. 팔로우 관계

### 문제

- 팔로우는 사용자 사이의 방향성 있는 관계다.
- 같은 관계가 중복 저장되거나 자기 자신을 팔로우할 수 없어야 하며, 요청 본문에 임의의 팔로워 ID를 넣어 다른 사용자로 행동할 수 없어야 한다.

### 근거와 도입 방법

**테이블과 제약**

- `follows` 테이블은 이력 행을 식별하는 `id` 대리 키와 관계의 두 당사자인 `follower_id`, `following_id`를 둔다.
- 언팔로우할 때 행을 지우지 않고 `deleted_at`에 삭제 시각을 기록한다. 다시 팔로우하면 기존 행을 복구하지 않고 새 행을 생성하여 팔로우·언팔로우 주기를 보존한다.
- `deleted_at IS NULL`인 활성 관계에만 `(follower_id, following_id)` 부분 유니크 인덱스를 적용한다. 따라서 과거 이력은 여러 건 남겨도 현재 활성 관계는 하나만 존재한다.
- 두 외래 키는 `users.id`를 참조하고, `CHECK (follower_id <> following_id)`는 애플리케이션 검증을 우회한 자기 팔로우도 DB에서 차단한다.
- 사용자 삭제 시에는 외래 키의 `ON DELETE CASCADE`로 해당 사용자와 관련된 팔로우 이력이 물리 삭제된다.

**API와 행위자**

- 팔로우 API는 `PUT /api/users/{followingId}/follow`, 언팔로우 API는 `DELETE /api/users/{followingId}/follow`다. 두 API 모두 반복 요청을 허용하고 상태가 원하는
  결과에 도달하면 `204 No Content`를 반환한다.
- 팔로워는 요청 값이 아니라 현재 Spring Security 인증 주체로 결정한다 — 컨트롤러가 `@AuthenticatedUser`로 세션 주체의 식별자(`AuthenticatedPrincipal.id` = Security
  principal = `users.id`)를 인증 컨텍스트에서 주입받아 서비스에 넘긴다.
- 엔티티를 주입하지 않으므로 행위자 조회가 없고, 대상 사용자 확인만 서비스 트랜잭션 안에서 한다.

**레이어별 책임**

- `follow.domain`: 관계 이력, 저장소 계약과 도메인 오류를 정의한다.
- `follow.application`: 행위자 ID 와 대상 사용자를 받아 자기 팔로우·대상 존재를 확인하고 팔로우 유스케이스를 조정한다.
- `follow.infrastructure`: PostgreSQL 원자 삽입·소프트 삭제와 팔로우 통계 행 증감·조회 쿼리를 구현한다.
- `follow.presentation`: HTTP 경로와 응답 계약을 제공한다.

### 결과

- 관계의 방향과 현재 상태가 명확하고, 애플리케이션과 DB가 자기 팔로우 및 활성 관계 중복을 이중으로 방지한다.
- 클라이언트 재시도는 별도 중복 오류 없이 안전하게 처리되며, 같은 사용자 쌍의 관계 변경 이력도 보존된다.

## 2. 팔로워 수와 팔로잉 수

### 문제

- 사용자 테이블에 카운터를 저장하면 관계 생성·삭제와 숫자 갱신을 항상 함께 유지해야 한다.
- 실패나 동시 요청으로 한쪽만 반영되면 실제 관계 수와 노출되는 숫자가 달라지고 별도의 보정 작업이 필요하다.

### 근거와 도입 방법

- 초기 단계에서는 `follows` 테이블을 직접 집계한다.

```sql
SELECT COUNT(*)
FROM follows
WHERE following_id = :userId
  AND deleted_at IS NULL;
SELECT COUNT(*)
FROM follows
WHERE follower_id = :userId
  AND deleted_at IS NULL;
```

- `(follower_id, following_id) WHERE deleted_at IS NULL` 부분 인덱스는 팔로잉 수 조회를 지원한다. 팔로워 수 조회를 위해
  `(following_id, follower_id) WHERE deleted_at IS NULL` 부분 인덱스를 별도로 둔다. 삭제된 행은 두 인덱스에서 제외되므로 활성 관계 집계 시 인덱스 크기를 제한한다.
- API는 `GET /api/users/{userId}/follow-stats`이며 `Long` 타입의 `followerCount`와 `followingCount`를 반환한다. 존재하지 않는 사용자는 `404 USER_NOT_FOUND`로
  처리한다.
- 실제 트래픽에서 집계가 병목으로 확인되기 전에는 Redis 카운터나 별도 통계 테이블을 도입하지 않는다.
- 향후 카운터가 필요해지면 관계 삽입·삭제가 실제로 발생한 경우에만 원자적인 증감 SQL을 실행하고, 원본 관계로 재계산할 수 있는 복구 절차를 함께 마련해야 한다.

### 결과

- 초기 단계에서는 팔로우 관계와 카운트가 항상 일치했다. 캐시 만료, 이중 저장소 정합성 및 카운터 유실 갱신 문제 없이 정확한 값을 제공했다.
- 이 절이 정한 재개봉 조건(집계 병목 실측)이 충족되어 아래 개정 절로 대체한다.

## 2. 팔로워 수와 팔로잉 수 — 개정

### 문제

- 초기 설계의 `COUNT` 직접 집계를 실측한 결과, `GET /api/users/{userId}/follow-stats`의 비용이 사용자의 **활성 관계 수에 비례**해 팔로워가 많은 사용자에서 병목이 된다는
  것이 확인됐다.
- 조회는 부분 인덱스 (`idx_follows_active_following`)만 훑는 Index Only Scan이지만 인덱스 페이지를 팔로워 수만큼 읽어야 한다. 팔로워 100만 사용자는 인덱스 페이지
  3,840개를 읽는 데 41 ms가 걸리고 PostgreSQL이 병렬 워커 2개를 띄운다.
- 통계 조회는 팔로우 쓰기보다 훨씬 잦고 인기 사용자에 편중되므로, 이 스캔이 DB 부하의 대부분을 차지하게 된다.

**실측 환경**

- PostgreSQL 17.11 (`postgres:17-alpine`, `shared_buffers` 128MB, `max_parallel_workers_per_gather` 2), Docker Desktop
  on Apple M3 Pro.
- 스키마는 `V1`~`V4`를 그대로 적용한 별도 DB.
- 데이터는 사용자 120만, `follows` 481만 행 (활성 331만, 소프트 삭제 이력 150만). 팔로워 수 분포는 1번 사용자 100만 · 2번 10만 · 3번 1만 · 4번 1천 · 5번 100 ·
  나머지 평균 10 내외.
- 단일 쿼리 수치는 캐시가 데워진 뒤 `EXPLAIN (ANALYZE, BUFFERS)` 5회 실행의 중앙값이다.

**단일 조회 지연**

| 팔로워 수 |  `COUNT(*)` 팔로워 수 1회 | 읽은 인덱스 페이지 | `follow_counts` PK 조회 1회 | 읽은 페이지 |
|----------:|--------------------------:|-------------------:|----------------------------:|------------:|
| 1,000,004 | **41.0 ms** (병렬 워커 2) |              3,840 |                 **0.07 ms** |           7 |
|   100,009 |                   10.6 ms |                390 |                     0.07 ms |           7 |
|    10,011 |                   1.18 ms |                 45 |                     0.07 ms |           7 |
|     1,011 |                   0.20 ms |                 11 |                     0.07 ms |           7 |
|       118 |                   0.11 ms |                  8 |                     0.07 ms |           7 |
|        10 |                   0.09 ms |                  7 |                     0.08 ms |           7 |

**동시 부하** — `pgbench`, 클라이언트 8, 요청의 5%가 1~5번 인기 사용자·95%가 일반 사용자, 15초.

| 통계 조회 방식                                            |         처리량 |    평균 지연 |
|-----------------------------------------------------------|---------------:|-------------:|
| `COUNT` × 2(팔로워 수 + 팔로잉 수, 초기 설계의 API 1회분) |     10,633 tps |     0.752 ms |
| `follow_counts` PK 조회 1회                               | **72,049 tps** | **0.111 ms** |

**해석**

- **개선 폭(팔로우 통계 행 도입으로 얻은 것)**
  - 단일 조회 지연: 팔로워 100만 **−99.8%**(41.0 → 0.07 ms, 586배), 10만 **−99.3%**(10.6 → 0.07 ms, 151배), 1만 **−94%**(1.18 → 0.07 ms), 1천 **−65%**
    (0.20 → 0.07 ms). 팔로워 100 이하에서는 차이가 0.04 ms 안이라 사실상 같다.
  - 혼합 부하 처리량: **+578%**(10,633 → 72,049 tps, 6.8배). 평균 지연 **−85%**(0.752 → 0.111 ms).
  - 읽은 페이지: 팔로워 100만 기준 3,840 → 7 페이지(**−99.8%**)로, 캐시가 식은 상태에서도 디스크 I/O가 팔로워 수에 비례해 늘지 않는다.
- 팔로워 1만 이하에서는 두 방식의 차이가 1 ms 안이지만, 10만에서 150배, 100만에서 600배로 벌어진다. `COUNT` 방식은 인기 사용자가 늘수록 나빠지는 반면, PK 조회는 팔로워 수와 무관하게
  일정하다.
- 쓰기 쪽 비용도 같은 환경에서 쟀다. 무작위 사용자 쌍의 팔로우 삽입(3절의 `ON CONFLICT … DO NOTHING`)만 실행하면 11,094 tps · 0.721 ms, 같은 트랜잭션에서 두 통계 행
  갱신을 함께 실행하면 9,109 tps · 0.878 ms(클라이언트 8, 10초, 실패·교착 0)다. 팔로우 쓰기 처리량 **−18%**(지연 +22%)를 치르는 대신 통계 조회가 활성 관계 수와 무관해지므로,
  조회가 쓰기보다 잦은 이 서비스에서는 받아들일 수 있는 교환이다.
- 초기 절이 카운터 도입 조건으로 요구한 "병목 실측"과 "관계 변경이 실제로 발생한 경우에만 증감 · 원본 관계로 재계산할 수 있는 복구 절차"를 그대로 이행한다.

### 근거와 도입 방법

**팔로우 통계 행**

- `follow_counts(user_id PK → users.id, follower_count, following_count)` 테이블 (`postgresql/V4`)에 사용자별 팔로우 통계 행을 둔다.
  `CHECK (>= 0)`으로 음수를 막고, 백필 SQL이 기존 활성 관계로 초기값을 채운다.
- 관계가 하나도 없는 사용자는 행이 없으며 조회 시 0으로 읽는다 (`FollowRepositoryAdapter.getCounts`).
- 마이그레이션이 `postgresql/V3`의 `deleted_at`에 의존하므로 `common/`이 아니라 `postgresql/`에 둔다.

**증감 규칙**

- 3절의 원자 SQL이 돌려주는 영향 행 수가 1일 때만, 즉 관계가 **실제로** 생성·소프트 삭제된 같은 트랜잭션 안에서 카운터를 바꾼다 (`FollowService.follow/unfollow`의
  `changed`). 멱등 재시도와 동시 요청은 영향 행 0이라 두 번 세지 않는다.
- 팔로우는 대상의 `follower_count`와 행위자의 `following_count`를 `INSERT … ON CONFLICT (user_id) DO UPDATE`로 +1 하고, 언팔로우는
  `UPDATE … WHERE follower_count >= :delta AND following_count >= :delta`로 −1 한다.
- 두 행은 항상 `user_id` 오름차순으로 갱신해 A→B와 B→A가 동시에 와도 교착이 나지 않는다 (`FollowRepositoryAdapter.forEachInLockOrder`).
- 관계 SQL과 카운터 SQL이 한 트랜잭션이므로 한쪽만 반영되는 경우는 없다.

**드리프트 신호**

- 감소 SQL의 영향 행이 0이면 (행이 없거나 이미 0) 관계는 있었는데 카운터가 없는 상태다. 요청은 성공시키고 warn 로그를 남긴다.
- 이 경우와 아래 CASCADE 경로가 카운터가 관계와 어긋날 수 있는 유일한 두 경로이며, 둘 다 재계산으로 복구한다.

**재계산 (복구) 절차**

- 원본은 항상 `follows`의 활성 관계다. 다음 SQL을 실행하면 모든 사용자의 통계 행이 활성 관계와 같아진다 (관계가 없는 사용자는 0 행이 생기며, 조회 결과는 동일하다).

```sql
INSERT INTO follow_counts (user_id, follower_count, following_count)
SELECT u.id,
       (SELECT COUNT(*) FROM follows f WHERE f.following_id = u.id AND f.deleted_at IS NULL),
       (SELECT COUNT(*) FROM follows f WHERE f.follower_id = u.id AND f.deleted_at IS NULL)
FROM users u ON CONFLICT (user_id) DO
UPDATE
    SET follower_count = EXCLUDED.follower_count,
    following_count = EXCLUDED.following_count;
```

- 실행 시점은 ① 위 warn 로그가 관측됐을 때 ② 사용자 행을 물리 삭제한 뒤 (아래) ③ 정기 점검이다.
- 진행 중인 팔로우 쓰기와는 행 잠금으로 직렬화되므로 서비스 중단 없이 실행할 수 있다.

**CASCADE 제약**

- `users` 행이 물리 삭제되면 그 사용자의 `follows` 이력과 `follow_counts` 행은 FK CASCADE로 함께 사라지지만, **그 사용자와 관계를 맺고 있던 상대방의 카운터는 줄지 않는다**
  (COUNT 집계에선 생길 수 없던 불일치).
- 현재 앱에는 사용자 삭제 API가 없어 수동 SQL로만 도달하는 경로이며, 그 경우 재계산 SQL을 곧바로 실행한다.
- 사용자 삭제 기능을 추가할 때는 삭제 트랜잭션 안에서 상대방 카운터를 먼저 감소시키는 것을 선행 조건으로 한다 ("현재 제약과 후속 판단").

**`COUNT` 쿼리의 역할**

- `countFollowers`/`countFollowing`은 운영 조회 경로에서 빠지고 **테스트의 대조 기준**으로만 남는다.
- `FollowApiTests`가 동시 팔로우·언팔로우 뒤 카운터와 `COUNT`가 같음을 실 PostgreSQL에서 검증한다.

### 결과

- 통계 조회 비용이 활성 관계 수와 무관하게 PK 조회 1회로 고정된다 — 실측 개선 폭은 팔로워 100만 사용자 지연 **−99.8%**(41 → 0.07 ms), 혼합 부하 처리량 **+578%**(6.8배),
  평균 지연 **−85%**. 대가는 팔로우 쓰기 처리량 −18%.
- 관계 변경과 카운터 갱신이 한 트랜잭션·한 저장소에 묶여 Redis 카운터 같은 이중 저장소 정합성 문제는 생기지 않는다.
- 어긋날 수 있는 두 경로 (감소 실패·사용자 물리 삭제)는 신호와 재계산 절차로 복구한다.

## 3. 동시성

### 문제

- 동일 사용자가 같은 대상을 동시에 팔로우하면 두 요청이 모두 관계가 없다고 판단할 수 있다.
- 애플리케이션의 사전 존재 확인만으로는 이 경쟁을 차단할 수 없고, 조회 후 삽입 방식은 DB 왕복도 추가한다.

### 근거와 도입 방법

- PostgreSQL을 팔로우 관계의 단일 진실 공급원으로 두고 다음 원자 SQL을 사용한다.

```sql
INSERT INTO follows (follower_id, following_id, created_at)
VALUES (:followerId, :followingId, CURRENT_TIMESTAMP) ON CONFLICT (follower_id, following_id)
WHERE deleted_at IS NULL DO NOTHING;
```

- 영향받은 행이 1개면 관계가 새로 생성됐고, 0개면 이미 활성 관계가 존재한다. 두 경우 모두 `PUT` 요청의 최종 목표가 충족됐으므로 성공으로 응답한다.
- 언팔로우는 활성 행만 다음과 같이 갱신한다.

```sql
UPDATE follows
SET deleted_at = CURRENT_TIMESTAMP
WHERE follower_id = :followerId
  AND following_id = :followingId
  AND deleted_at IS NULL;
```

- 영향받은 행이 없어도 이미 언팔로우 상태이므로 `DELETE` API는 멱등하게 성공한다. 다시 팔로우하면 삭제된 행은 부분 유니크 인덱스의 대상이 아니므로 새 활성 행이 삽입된다.
- 이 두 쿼리는 부분 유니크 인덱스와 `deleted_at IS NULL` 조건을 공유한다. 그러므로 동시 팔로우는 활성 행 하나로 수렴하고, 동시 언팔로우는 활성 행을 한 번만 삭제 상태로 바꾼다.
- Redis 분산 잠금은 사용하지 않는다. 관계 데이터가 PostgreSQL에 있으므로 같은 저장소의 제약과 원자 SQL이 더 작은 장애 범위로 정확성을 보장한다. Redis 장애가 팔로우 쓰기 경로에
  전파되지 않으며 잠금 TTL이나 해제 실패도 관리할 필요가 없다.
- 자동 테스트는 실제 PostgreSQL 17 Testcontainers에서 8개 요청을 동시에 실행한다. 모든 요청이 멱등 성공하고 최종 관계 행과 팔로워 수가 하나인지 검증한다.
- 테스트 DB 는 API 테스트 전부가 운영과 같은 PostgreSQL 이며 H2 는 쓰지 않는다 — H2 는 `ON CONFLICT (…) WHERE …` 충돌 대상 문법을 파싱하지 못해 팔로우 삽입 경로 자체를
  실행할 수 없고, 부분 인덱스도 만들지 못해 동시성의 근거가 되지 않는다.

### 결과

- 동일 관계에 대한 동시·반복 팔로우가 하나의 활성 행으로 수렴한다.
- 서로 다른 사용자의 관계는 불필요한 전역 잠금 없이 병렬 처리되며, 팔로우 통계 행도 관계가 실제로 바뀐 트랜잭션에서만 갱신되어 활성 관계와 일치한다.

## 4. PostgreSQL 선택

### 문제

- 팔로우 관계는 소프트 삭제로 이력 행이 계속 쌓이면서도 "현재 활성 관계"에 대한 유일성 보장과 집계는 빠르고 정확해야 한다.
- 팔로워 수 조회 같은 읽기 요청이 동시에 진행 중인 팔로우·언팔로우 쓰기와 서로를 기다리지 않아야 한다.
- 저장소가 이 두 요구를 자체 기능으로 지원하지 않으면 애플리케이션이 잠금이나 별도 상태 테이블로 보완해야 한다.

### 근거와 도입 방법

- 관계 저장소로 PostgreSQL을 선택한 이유는 다음 두 가지다.

  1. **소프트 삭제 쿼리에 최적화된 부분 인덱스를 도입할 수 있다.** `WHERE deleted_at IS NULL` 조건이 붙은 부분 인덱스는 활성 관계 행만 담는다. 활성 관계 유일성
     (`uk_follows_active_relation`)과 팔로워·팔로잉 집계 인덱스가 삭제된 이력 행의 영향을 받지 않고,
     `INSERT ... ON CONFLICT ... WHERE deleted_at IS NULL DO NOTHING`의 중재 인덱스로 그대로 사용할 수 있다. 부분 인덱스가 없는 저장소에서는 이력 행까지 포함한
     전체 인덱스를 유지하거나 활성 관계를 별도 테이블로 분리해야 한다.
  2. **기본 격리 수준인 READ COMMITTED에서 높은 읽기 성능을 보장한다.** PostgreSQL은 MVCC로 읽기와 쓰기가 서로를 차단하지 않으므로, 팔로우 통계 조회 같은 읽기 트랜잭션이 동시에
     커밋되는 팔로우·언팔로우 쓰기를 기다리지 않는다. 팔로우 쓰기 경로의 정확성은 격리 수준이 아니라 3절의 부분 유니크 인덱스와 원자 SQL이 보장하므로, 읽기 경로에 더 높은 격리 수준을
     요구하지 않는다.

**Flyway 마이그레이션과 테스트 DB**

- Flyway 마이그레이션은 벤더별로 나눈다. `spring.flyway.locations`는 `classpath:db/migration/common,classpath:db/migration/{vendor}`이며, 벤더 중립
  DDL (`V1`, `V2`)은 `common/`, 부분 인덱스를 쓰는 `V3`와 `V3`의 `deleted_at`에 의존하는 `V4`(팔로우 통계 행)는 `src/main/resources/db/migration/postgresql/`에
  둔다.
- 처음에는 H2 (PostgreSQL 모드)를 테스트 DB 로 쓰기 위해 `src/test/resources/db/migration/h2/V3` 대체본을 두었으나, H2 는 부분 인덱스를 만들지 못해 활성 관계 유일성을
  강제하지 않고 `ON CONFLICT (…) WHERE …` 문법도 파싱하지 못해 팔로우 삽입 경로를 실행조차 할 수 없었다.
- 따라서 **테스트 DB 도 PostgreSQL 17 로 통일**했다 — 모든 `@SpringBootTest`·`@DataJpaTest` 가 JVM 당 하나의 Testcontainers PostgreSQL 을 공유하며
  (`@PostgresTest`), H2 의존성과 대체 마이그레이션은 제거했다. 벤더 디렉터리 분리는 `{vendor}` 자리표시자로 유지하되 현재 `postgresql/` 하나만 있다.
- 소프트 삭제 갱신 쿼리는 HQL의 `CURRENT_TIMESTAMP`가 `Instant` 필드에 대입되지 않아 native SQL로 작성한다.

### 결과

- 이력 행이 늘어나도 활성 관계의 유일성 검사 비용은 활성 행 수에만 비례하고, 읽기 요청이 쓰기 요청과 잠금을 두고 경쟁하지 않는다.
- 그 결과 별도의 활성 관계 테이블이나 읽기 전용 복제 저장소 없이 단일 PostgreSQL로 현재 범위의 요구를 충족한다.

## 현재 제약과 후속 판단

- 같은 관계에 대한 팔로우와 언팔로우가 동시에 실행되면 DB 커밋 순서가 최종 상태를 결정한다.
- 요청 도착 순서까지 보장해야 한다면 관계 버전이나 PostgreSQL advisory transaction lock을 추가로 검토한다.
- 소프트 삭제로 이력 행이 계속 늘어난다. 보존 기간과 개인정보 정책이 확정되면 아카이브·물리 삭제 배치와 PostgreSQL `VACUUM` 운영 기준을 함께 정의한다.
- 팔로워 목록과 팔로잉 목록 API, 페이지네이션 및 차단 사용자 정책은 현재 범위에 포함하지 않는다.
- 집계 병목이 실측되어 팔로우 통계 행 (`follow_counts`)을 도입했다 ("2. 팔로워 수와 팔로잉 수 — 개정"). Redis 카운터·캐시는 여전히 도입하지 않는다 — 이중 저장소 정합성 문제가 다시
  생긴다.
- 사용자 물리 삭제는 상대방의 팔로우 통계 행을 줄이지 않는다. 사용자 삭제 기능을 넣을 때는 삭제 트랜잭션 안에서 상대방 카운터 감소를 먼저 하고, 그 전까지 수동 삭제 뒤에는 재계산 SQL을 실행한다.
