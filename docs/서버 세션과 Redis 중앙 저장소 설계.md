# 서버 세션과 Redis 중앙 저장소 설계

## 문서 목적과 범위

- 이 문서는 SNS 애플리케이션의 서버 세션과 Redis 중앙 저장소 설계만 다룬다. 로컬 실행 명령과 환경 변수 사용 예시는 루트의 `README.md`에서 관리한다.
- 사용자 도메인, API 오류 계약, 데이터베이스 스키마, 패키지 구조와 일반 테스트 전략은 이 문서의 범위에서 제외한다.
- 현재 인증 상태는 클라이언트가 자체적으로 해석하는 토큰이 아니라 서버가 관리하는 HTTP 세션으로 표현한다. 세션의 실제 데이터는 각 애플리케이션 인스턴스의 메모리가 아니라 Redis에 저장한다.

## 서버 세션과 Redis 중앙 저장소

### 문제

#### 인스턴스 메모리 세션의 한계

기본 서블릿 세션은 애플리케이션 프로세스의 메모리에 저장된다. 인스턴스가 하나일 때는 단순하지만 다음 문제가 발생한다.

- 애플리케이션을 재시작하거나 배포하면 메모리에 있던 로그인 상태가 모두 사라진다.
- 인스턴스를 여러 개 실행하면 각 인스턴스가 서로 다른 세션 집합을 가진다.
- 로드 밸런서가 요청을 다른 인스턴스로 전달하면 사용자가 갑자기 로그아웃된 것처럼 보일 수 있다.
- sticky session으로 특정 인스턴스에 요청을 고정할 수 있지만 장애 조치와 부하 분산의 유연성이 낮아진다.
- 로그아웃, 강제 만료와 동시 로그인 제한을 전체 인스턴스에 일관되게 반영하기 어렵다.

#### 인증 상태의 즉시 통제 필요

- 현재 요구사항에는 로그아웃과 사용자당 최대 세션 수 1개 제한이 포함된다.
- 인증 상태를 서버가 중앙에서 조회할 수 없다면 이미 발급된 인증 정보를 즉시 무효화하거나 다른 인스턴스에 존재하는 로그인 여부를 판단하기 어렵다.

#### 세션 저장소 장애의 영향

- 중앙 저장소를 도입하면 애플리케이션 메모리의 문제는 해결되지만 인증 요청이 외부 저장소에 의존하게 된다.
- Redis의 지연이나 장애가 모든 로그인 세션에 영향을 줄 수 있으므로 저장 방식뿐 아니라 장애 시 동작, 만료, 보안과 운영 조건까지 함께 결정해야 한다.

### 근거와 도입 방법

#### 1. 서버 세션을 선택한 이유

- 현재 인증은 서버 세션 방식을 사용한다. 클라이언트에는 의미 없는 세션 식별자만 쿠키로 전달하고, 인증 주체와 CSRF 토큰 같은 실제 상태는 서버 저장소에 둔다.
- 이 방식은 다음 요구사항에 적합하다.
    - 로그아웃 시 서버 저장소에서 세션을 제거해 즉시 인증을 무효화할 수 있다.
    - 탈취가 의심되는 세션이나 정책상 허용되지 않는 세션을 서버가 통제할 수 있다.
    - 사용자별 활성 세션을 조회해 동시 로그인 정책을 적용할 수 있다.
    - 클라이언트가 인증 상태 구조와 권한 정보를 직접 보관하거나 해석하지 않는다.
- 자체 완결형 JWT는 매 요청마다 중앙 저장소를 조회하지 않아도 된다는 장점이 있지만, 만료 전에 즉시 폐기하려면 별도의 차단 목록이나 토큰 버전 저장소가 다시 필요하다.
- 현재 요구사항은 무상태성보다 즉시 무효화와 중앙 통제가 중요하므로 JWT 대신 서버 세션을 선택했다.

#### 2. Redis를 중앙 저장소로 선택한 이유

- Redis는 세션처럼 짧은 수명과 빈번한 읽기·쓰기를 가진 데이터를 메모리에서 처리하고 키별 TTL을 지원한다.
- Spring Session이 Redis 저장소와 서블릿 세션을 통합하므로 애플리케이션 코드가 Redis 명령을 직접 실행하지 않고도 표준 `HttpSession` 계약을 유지할 수 있다.
- 다른 선택지와 비교한 판단은 다음과 같다.

| 선택지                 | 제외하거나 제한한 이유                                                                                       |
|------------------------|--------------------------------------------------------------------------------------------------------------|
| 인스턴스 메모리        | 재시작과 다중 인스턴스에서 세션을 공유할 수 없다.                                                            |
| Sticky session         | 로드 밸런서와 특정 인스턴스의 결합이 생기며 인스턴스 장애 시 세션을 잃는다.                                  |
| PostgreSQL 세션 테이블 | 구현은 가능하지만 인증 요청마다 관계형 DB 부하가 증가하고 TTL 기반 정리와 고빈도 갱신에 Redis가 더 적합하다. |
| 자체 완결형 JWT        | 즉시 로그아웃과 사용자별 동시 세션 제한을 위해 별도의 중앙 상태가 다시 필요하다.                             |
| Redis                  | 외부 저장소 의존성과 운영 비용이 생기지만 공유, TTL, 조회 성능과 Spring Session 통합 요구를 충족한다.        |

#### 3. 전체 구성

```text
                           ┌──────────────────────────┐
Client ── SESSION cookie ─▶│ Application instance A   │
                           │ Spring Security          │
                           │ Spring Session           │
                           └────────────┬─────────────┘
                                        │
                                        │ shared session read/write
                                        ▼
                               ┌─────────────────┐
                               │ Redis           │
                               │ sns:session:*   │
                               └─────────────────┘
                                        ▲
                                        │ shared session read/write
                           ┌────────────┴─────────────┐
Client ── SESSION cookie ─▶│ Application instance B   │
                           │ Spring Security          │
                           │ Spring Session           │
                           └──────────────────────────┘
```

- 모든 애플리케이션 인스턴스는 같은 Redis를 바라본다. 클라이언트가 어느 인스턴스로 요청하더라도 쿠키의 세션 ID로 동일한 인증 상태를 조회한다.
- 이 설계는 세션 유지를 위해 로드 밸런서의 sticky session에 의존하지 않는다.

#### 4. Spring Session 구성

- `spring-boot-starter-session-data-redis`가 서블릿 컨테이너의 세션 저장을 Spring Session으로 대체한다. 설정은 성격에 따라 연결 정보와 세션 정책으로 나눈다.
- Redis 호스트·포트·비밀번호는 배포 환경마다 다르고 비밀번호를 코드에 포함해서는 안 되므로 `application.yaml`에서 환경 변수로 외부화한다.

```yaml
spring:
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
      password: ${REDIS_PASSWORD:}
      repositories:
        enabled: false
```

- 반면 세션 유효 시간, 키 네임스페이스, 저장 시점과 indexed repository 사용 여부는 모든 인스턴스가 동일하게 지켜야 하는 애플리케이션 정책이다. 이 값들은 `RedisSessionConfig`의
  Spring 구성으로 관리한다.

```kotlin
@Configuration
@Profile("!test")
@EnableRedisIndexedHttpSession(
    maxInactiveIntervalInSeconds = 30 * 60,
    redisNamespace = "sns:session",
    flushMode = FlushMode.ON_SAVE,
    saveMode = SaveMode.ON_SET_ATTRIBUTE,
)
class RedisSessionConfig
```

- `@EnableRedisIndexedHttpSession`은 `RedisIndexedSessionRepository`를 포함한 Spring Session 기반 빈을 등록한다. 따라서 이 구성은 단순 상수 모음이
  아니라 기본 서블릿 세션 저장소를 Redis 구현으로 교체하는 런타임 구성이다.
- 세션 정책을 YAML 환경 변수로 임의 변경할 수 없게 함으로써, 일부 인스턴스만 다른 TTL이나 네임스페이스를 사용해 활성 세션과 사용자 인덱스가 갈라지는 상황을 방지한다. 정책 변경에는 코드 리뷰, 테스트와
  전체 인스턴스 재배포가 필요하다.
- 각 설정의 역할은 다음과 같다.

| 설정                            |             기본값 | 역할                                                              |
|---------------------------------|-------------------:|-------------------------------------------------------------------|
| `REDIS_HOST`                    |        `localhost` | Redis 호스트를 지정한다.                                          |
| `REDIS_PORT`                    |             `6379` | Redis 포트를 지정한다.                                            |
| `REDIS_PASSWORD`                |              빈 값 | 인증이 설정된 외부 Redis의 비밀번호를 전달한다.                   |
| `maxInactiveIntervalInSeconds`  |             `1800` | 마지막 요청 이후 세션이 유효한 최대 시간을 지정한다.              |
| `redisNamespace`                |      `sns:session` | 다른 애플리케이션의 키와 충돌하지 않도록 접두사를 지정한다.       |
| `flushMode`                     |          `ON_SAVE` | 요청 종료 시 변경된 세션을 Redis에 반영한다.                      |
| `saveMode`                      | `ON_SET_ATTRIBUTE` | 변경된 세션 속성만 저장해 불필요한 쓰기를 줄인다.                 |
| `EnableRedisIndexedHttpSession` |             활성화 | principal(사용자 ID)로 세션을 역조회할 수 있는 저장소를 사용한다. |

- Redis는 HTTP 세션 저장소로만 사용한다. Redis 엔티티 Repository가 없으므로 `spring.data.redis.repositories.enabled=false`로 불필요한 Repository
  탐색을 막는다.
- 테스트에서는 `test` 프로필이 `RedisSessionConfig`를 제외하고 `MapSessionRepository`를 주입한다. 이에 따라 일반 테스트가 외부 Redis 가용성에 의존하지 않으면서도, 운영
  코드에서는 indexed Redis 저장소만 사용한다.

#### 5. indexed repository와 동시 로그인 제한

- 기본 세션 저장소는 세션 ID로 세션을 찾는 데 충분하지만 사용자별 활성 세션 목록을 조회하려면 인덱스가 필요하다. 따라서 `RedisIndexedSessionRepository`와
  `SpringSessionBackedSessionRegistry`를 사용한다.
- 로그인 시 세션 전략은 다음 순서로 실행된다.

1. 인증된 principal (사용자 ID)의 SHA-256 해시를 키로 `SET NX`를 실행해 로그인 임계 구역을 원자적으로 획득한다.
2. 잠금 획득에 실패하면 같은 사용자의 로그인이 이미 진행 중이므로 `409 SESSION_LIMIT_EXCEEDED`를 반환한다.
3. `ConcurrentSessionControlAuthenticationStrategy`가 Redis의 사용자 인덱스로 기존 활성 세션을 조회한다.
4. 활성 세션이 이미 하나라면 새 로그인을 중단하고 `409 SESSION_LIMIT_EXCEEDED`를 반환한다.
5. 활성 세션이 없다면 `ChangeSessionIdAuthenticationStrategy`가 로그인 전 세션 ID를 새로운 값으로 교체한다.
6. `SecurityContextRepository`가 인증 결과를 세션에 저장한다.
7. Spring Session이 요청 종료 시 세션과 사용자 인덱스를 Redis에 커밋한 뒤 로그인 잠금을 해제한다.

- 활성 세션 조회와 신규 세션 저장은 서로 다른 Redis 연산이므로 조회만으로는 두 인스턴스의 동시 로그인을 막을 수 없다. 두 요청이 모두 세션 수 0을 읽는 경쟁을 차단하기 위해
  `RedisLoginConcurrencyGuard`가 사용자별 로그인 과정을 직렬화한다.
- 잠금 값은 요청별 UUID이며 Lua 스크립트가 소유 토큰이 일치할 때만 키를 삭제하므로, TTL 만료 후 다른 요청이 획득한 잠금을 이전 요청이 삭제할 수 없다.
- 잠금 해제 필터는 `SessionRepositoryFilter`보다 먼저 실행되고 나중에 종료된다. 따라서 Spring Session의 `commitSession()`이 완료될 때까지 잠금이 유지되고, 다음
  요청은 Redis 사용자 인덱스가 생성된 이후에만 진입한다.
- 프로세스 종료나 네트워크 단절로 해제하지 못한 잠금은 1분 TTL로 복구한다. 로그인 요청의 최대 처리 시간은 이 TTL보다 짧도록 운영 타임아웃을 설정해야 한다.
- 기존 세션을 종료하고 새 로그인을 허용하는 방식도 가능하지만, 현재 정책은 기존 사용자의 작업을 보존하기 위해 기존 세션을 유지하고 새 로그인을 거부한다. 기존 사용자가 로그아웃하면 Redis의 사용자 인덱스에서
  활성 세션이 사라지므로 다른 클라이언트가 로그인할 수 있다.

#### 6. 요청별 세션 생명주기

##### CSRF 토큰 조회

1. 클라이언트가 `GET /api/auth/csrf`를 호출한다.
2. 서버는 CSRF 토큰을 세션에 연결하고 세션 쿠키를 반환한다.
3. 클라이언트는 이후 상태 변경 요청에 같은 쿠키와 CSRF 헤더를 함께 전송한다.

- 로그인 이전에도 CSRF 토큰 보관을 위한 익명 세션이 존재할 수 있다. 이 세션은 아직 인증 사용자 인덱스에 포함되지 않으므로 동시 로그인 수로 계산하지 않는다.

##### 로그인

1. Spring Security가 이메일과 비밀번호를 검증한다.
2. Redis에서 사용자별 로그인 잠금을 원자적으로 획득한다.
3. Redis의 사용자 인덱스로 기존 로그인 세션 수를 확인한다.
4. 로그인이 허용되면 세션 고정 공격을 막기 위해 세션 ID를 교체한다.
5. 인증된 `SecurityContext`를 새 세션에 저장한다.
6. 응답의 세션 쿠키가 새 ID로 갱신되고 세션이 Redis에 커밋된다.
7. 세션 커밋 이후 사용자별 로그인 잠금을 해제한다.

##### 인증된 요청

1. Spring Session 필터가 쿠키에서 세션 ID를 읽는다.
2. Redis에서 세션과 `SecurityContext`를 조회한다.
3. Spring Security가 조회된 인증 주체를 현재 요청의 보안 컨텍스트로 복원한다.
4. 요청 중 세션이 변경되면 요청 종료 시 Redis에 저장한다.

##### 로그아웃

1. CSRF 검증을 통과한 `POST /api/auth/logout` 요청을 처리한다.
2. SecurityContext를 비우고 현재 HTTP 세션을 무효화한다.
3. Redis의 활성 세션과 사용자 인덱스를 제거한다.
4. 클라이언트 세션 쿠키를 만료시킨다.

- Indexed repository는 세션 삭제와 만료 이벤트 전파를 위해 로그아웃 후 짧은 시간 동안 만료 표식이나 보조 키를 남길 수 있다. 이 키는 활성 사용자 인덱스에 포함되지 않으며 로그인된 세션으로
  계산되지 않는다.

#### 7. Redis 키와 저장 데이터

**저장 데이터** — 기본 네임스페이스가 `sns:session`일 때 Redis에는 개념적으로 다음 종류의 데이터가 저장된다.

- 세션 ID별 세션 해시
- principal (사용자 ID)에서 세션 ID를 찾기 위한 인덱스
- TTL 만료 처리와 이벤트 발행을 위한 보조 키
- 동시 로그인 요청을 직렬화하는 `sns:session:login-lock:*` 임시 키
- `SecurityContext`, CSRF 토큰과 기타 세션 속성

**키 형식**

- 실제 키 형식은 Spring Session 구현 세부사항이며 애플리케이션 코드가 키 문자열을 조합해 직접 접근하지 않는다.
- 운영 도구도 키 내부 형식에 의존하기보다 Spring Session이 제공하는 저장소 계약을 우선해야 한다.

**principal = `users.id`**

- Spring Security principal (`Authentication.name`)은 이메일이 아니라 **`users.id`의 10진 문자열**이다. 로그인 입력은 이메일이지만
  `UserDetailsService`가 principal을 ID로 만든다.
- 그 이유는 ① ID는 불변이라 이메일 변경이 생겨도 세션 인덱스·잠금 키가 옛 값에 묶이지 않고, ② Redis 인덱스 키와 로그에 개인정보가 남지 않으며, ③ 행위자가 필요한 요청마다 이메일로 사용자를 다시
  조회하지 않아도 되기 때문이다.
- ID와 이메일을 함께 담는 커스텀 `UserDetails`는 아래 직렬화 호환 원칙과 충돌하므로 두지 않고, Spring이 제공하는 `User` 클래스만 세션에 남긴다.
- 이 규칙 이전에 만들어진 세션 (principal이 이메일)은 배포 후 인증 주체를 주입받는 요청에서 401로 거부되어 재로그인이 필요하다. 세션 자체는 TTL까지 Redis에 남고 인덱스 값이 이메일이라 새
  로그인의 동시 세션 수에 포함되지 않는다.
- 옛/새 버전이 섞인 롤링 배포 중에는 잠금 키가 갈려 동시 로그인이 직렬화되지 않는다. 따라서 전환은 일괄 배포하거나 배포 직후 `sns:session:*` 키를 비운다.

**직렬화 호환**

- 세션 속성은 Redis serializer를 통해 저장된다. 세션에 임의의 도메인 객체를 추가하면 클래스 구조 변경과 배포 버전 차이로 역직렬화가 실패할 수 있다.
- 현재처럼 필요한 보안 컨텍스트만 저장하고, 커스텀 세션 속성을 추가할 때는 직렬화 호환성과 롤링 배포 영향을 검토해야 한다.

#### 8. 쿠키와 전송 보안

- Redis에 인증 상태를 저장하더라도 세션 ID 쿠키가 탈취되면 공격자가 해당 세션을 사용할 수 있다. 현재 쿠키 정책은 다음과 같다.
    - `HttpOnly=true`: 브라우저 JavaScript가 세션 쿠키를 직접 읽지 못하게 한다.
    - `SameSite=Lax`: 일반적인 교차 사이트 요청에서 쿠키 전송을 제한한다.
    - `Secure`: 로컬 HTTP 개발 환경에서는 기본값이 `false`이며 운영 HTTPS에서는 반드시 `SESSION_COOKIE_SECURE=true`로 설정한다.
    - CSRF 토큰: 상태 변경 요청은 세션 쿠키 외에 올바른 CSRF 토큰도 요구한다.
    - 로그인 성공 시 세션 ID 교체: 공격자가 로그인 전에 확보한 세션 ID를 인증 세션으로 재사용하는 것을 방지한다.
- 세션 ID 자체는 인증 정보가 아니라 Redis 데이터를 찾는 임의 식별자여야 한다. 로그, 오류 응답과 모니터링 태그에 원본 세션 ID를 남기지 않는다.

#### 9. 로컬 Redis 구성과 운영 환경 차이

- 로컬 환경은 Docker Compose에서 Redis 7.4 Alpine 이미지를 사용한다.

```yaml
redis:
  image: redis:7.4-alpine
  command: [ "redis-server", "--appendonly", "yes" ]
  volumes:
    - redis-data:/data
  healthcheck:
    test: [ "CMD", "redis-cli", "ping" ]
```

- AOF와 named volume은 로컬 컨테이너 재시작 시 세션 데이터를 보존한다. 그러나 이 구성은 개발 편의를 위한 단일 노드이며 운영 고가용성을 제공하지 않는다.
- 운영 환경에서는 다음 항목을 별도로 결정해야 한다.
    - Redis Sentinel, Cluster 또는 관리형 서비스에 의한 고가용성
    - TLS, ACL과 네트워크 접근 통제
    - 자격증명의 비밀 저장소 연동과 주기적 교체
    - 세션 총량을 고려한 메모리 크기와 경보 임계치
    - 활성 세션이 임의로 제거되지 않도록 하는 eviction 정책
    - 백업·복구 시 오래된 인증 세션을 복원할지 여부
    - Redis와 애플리케이션 간 타임아웃, 재시도와 커넥션 풀 설정
    - 세션 조회 지연, 오류율, 활성 세션 수와 만료량 모니터링

#### 10. 장애 시 동작 원칙

- Redis에서 세션을 읽지 못하면 서버는 사용자를 인증된 상태로 추정해서는 안 된다. 현재 구조는 유효한 세션을 복원하지 못한 요청을 인증된 요청으로 통과시키지 않는 fail-closed 방향이다.
- Redis 장애 중 애플리케이션 메모리에 임시 세션을 생성하는 폴백은 사용하지 않는다. 이런 폴백은 인스턴스마다 다른 인증 상태를 만들고, Redis 복구 후 어떤 세션을 신뢰할지 결정하기 어렵게 한다.
- 다만 저장소 연결 실패가 항상 정형화된 API 오류로 변환되는 것은 아직 보장하지 않는다. 운영 도입 전에는 다음 정책을 추가로 결정해야 한다.
    - Redis 연결 실패를 클라이언트에 `503 Service Unavailable`로 표현할지 여부
    - 읽기와 쓰기 타임아웃 값
    - 재시도가 로그인 요청을 중복 처리하지 않도록 하는 범위
    - 장애 시 신규 로그인 차단과 기존 요청 처리 정책
    - 복구 후 세션 인덱스 정합성 확인 방법

#### 11. 검증 전략

- 자동화된 테스트는 책임을 다음과 같이 나눈다.
    - 로그인 서비스 테스트는 자격증명 인증과 사용자 조회 결과를 검증한다.
    - 세션 인증 서비스 테스트는 세션 전략 적용과 SecurityContext 저장을 검증한다.
    - 세션 보안 테스트는 로그인 세션 조회, 로그아웃, CSRF와 미인증 접근을 검증한다. 세션은 유효하나 `users` 행이 없는 경우도 404가 아니라 401로 거부되는지 함께 검증한다.
    - 동시 세션 테스트는 같은 사용자의 두 번째 로그인이 거부되는 계약을 검증한다.
    - Redis 동시성 가드 테스트는 실제 Redis 컨테이너에 동시에 `SET NX`를 실행해 하나의 요청만 잠금을 획득하는지 검증한다.
    - Redis 세션 통합 테스트는 운영과 같은 indexed repository에서 병렬 로그인 결과가 성공 1건·충돌 1건이고 활성 세션이 하나만 남는지 검증한다.
    - 일반 빌드는 외부 Redis 가용성에 의존하지 않도록 테스트용 인메모리 세션 저장소를 사용한다.
- 실제 Redis 검증에서는 다음 동작을 확인했다.
    1. 로그인 후 `sns:session` 네임스페이스에 세션이 생성된다.
    2. 애플리케이션을 재시작해도 같은 쿠키로 인증 상태를 복원한다.
    3. 첫 세션이 활성 상태일 때 다른 클라이언트의 로그인은 `409 SESSION_LIMIT_EXCEEDED`로 거부된다.
    4. 첫 세션이 로그아웃하면 두 번째 클라이언트가 로그인할 수 있다.
    5. 로그아웃 후 활성 사용자 세션 인덱스가 제거된다.
- 로그인 잠금의 원자적 획득·해제와 병렬 로그인 시 단일 활성 세션 보장은 Testcontainers 기반 Redis 통합 테스트에 포함된다. Docker를 사용할 수 없는 환경에서는 이 테스트가 건너뛰어진다.
- 애플리케이션 재시작 복원과 실제 Redis 로그아웃 삭제 검증은 아직 수동 통합 검증이며, 이후 별도 인프라 통합 테스트로 자동화할 수 있다.

### 결과

#### 확보한 특성

- 애플리케이션 재시작 후에도 TTL이 남은 세션을 복원할 수 있다.
- 여러 애플리케이션 인스턴스가 동일한 인증 상태를 공유한다.
- 로드 밸런서의 sticky session 없이 요청을 분산할 수 있다.
- 로그아웃으로 인증 상태를 서버에서 즉시 무효화할 수 있다.
- Redis 사용자 인덱스를 기준으로 전체 인스턴스에 사용자당 하나의 활성 세션 정책을 적용한다.
- 세션 ID 교체, CSRF, HttpOnly와 SameSite 쿠키 정책을 함께 적용한다.

#### 수용한 비용과 제약

- 인증된 요청마다 Redis 접근이 발생하므로 Redis 지연이 요청 지연에 포함된다.
- Redis가 인증 경로의 핵심 의존성이자 단일 장애 지점이 될 수 있다.
- 세션 데이터와 애플리케이션 클래스의 직렬화 호환성을 관리해야 한다.
- 다중 리전에서는 Redis 왕복 지연과 리전 간 일관성 정책을 별도로 설계해야 한다.
- 현재 Docker Compose는 단일 Redis 노드이므로 운영 고가용성의 근거가 되지 않는다.
- 실제 Redis 회귀 검증이 기본 자동 테스트에 포함되어 있지 않다.

#### 완료 기준과 후속 과제

- 현재 로컬 개발 범위에서는 Redis 공유 세션 생성, 재시작 후 복원, 동시 로그인 제한과 로그아웃 삭제가 확인되었다.
- 운영 환경으로 확장하기 전에는 다음 항목을 완료해야 한다.
1. 관리형 Redis 또는 고가용성 토폴로지를 선택한다.
2. TLS, ACL, 비밀 관리와 네트워크 격리를 적용한다.
3. `SESSION_COOKIE_SECURE=true`를 강제하는 운영 설정을 마련한다.
4. Redis 장애를 `503` 등 일관된 API 오류로 변환하는 정책을 정의한다.
5. 세션 수, Redis 지연, 연결 실패와 eviction을 감시하는 지표와 경보를 구성한다.
6. Testcontainers 기반 Redis 통합 테스트 도입 여부를 결정한다.
7. 배포 간 세션 직렬화 호환성과 필요 시 전체 세션 무효화 절차를 문서화한다.
