# 미디어 (이미지) 업로드·첨부 설계

## 문서 목적과 범위

- 게시글·답글·인용에 **이미지를 붙이는** 기능의 결정 이력이다. 바이트 저장소는 **Amazon S3**, 메타데이터는 PostgreSQL `media` 테이블 (`postgresql/V6`).
- 이 문서로 GLOSSARY §0 의 경계 "첨부 없음" 을 개정한다 (2026-09-20, 사용자 요청). 동영상 · 썸네일/리사이즈 · 미디어 삭제 API · 미첨부 미디어 정리 · 미디어만 있는 게시글은
  여전히 범위 밖이며 "현재 제약과 후속 판단" 에 적는다.
- 용어: **미디어** = `media` 행 하나 (= S3 객체 하나). **업로드 URL** = presigned PUT. **완료** = `POST …/complete` 로 `READY` 가 되는 것.
  **첨부** = 게시글 작성 트랜잭션에서
  `media.post_id` 가 채워지는 것.

## 1. 업로드 흐름 — 클라이언트가 S3 에 직접 PUT

### 문제

이미지 바이트가 애플리케이션 서버를 거치면 요청당 최대 10MB 를 서블릿 스레드가 들고 있어야 한다. 이미지 업로드는 이 서비스에서 가장 큰 요청이 되고, 서버 대역폭·메모리가 곧 업로드 처리량 상한이 된다.
반대로 클라이언트가 S3 에 직접 쓰게 하면 "무엇이 올라왔는지" 를 서버가 모른다.

### 근거와 도입 방법

- **3단계**: ① `POST /api/media/uploads {contentType, sizeBytes}` → 서버가 `media` 행을 `PENDING` 으로 만들고 **presigned PUT** 을 준다
  ② 클라이언트가 그 URL 로 S3 에 PUT ③ `POST /api/media/{mediaId}/complete` → 서버가 S3 `HEAD` 로 객체를 확인하고 내용을 검증한 뒤 `READY`.
- **선언값이 서명에 묶인다**: presigned PUT 에 `Content-Type` 과 `Content-Length` 를 서명 헤더로 넣는다 (`S3MediaStorage.presignUpload`).
  클라이언트가 다른 타입·길이로 PUT 하면 S3 가 403 으로 거부하므로, 완료 시점의 `HEAD` 는 "올라왔는가" 와 "선언과 같은가" 를 둘 다 확인하는 것이 된다. 서명 헤더 집합
  (`X-Amz-SignedHeaders` 에 `content-type`·`content-length`)은 `S3MediaStoragePresignTests` 가 확인하고, 실제 거부는 실 S3 에서만 보인다
  (수동 확인 지점, §5).
- **presign 은 네트워크가 없다** — SigV4 서명은 로컬 계산이라 트랜잭션 안에서 불러도 된다. `HEAD`·`GET`·`DELETE` 는 S3 왕복이라 (`HEAD`·`GET` 은 `MediaVerifier.verify`, `DELETE` 는 `MediaUploadService.complete` 의 폐기 분기) `MediaUploadService` 는
  `@Transactional` 을 두지 않고 DB 쓰기를 원자 SQL 한 문장씩으로 한다 (`save` · `markReady` · `softDeletePending`) —
  `rules/stack-kotlin-spring.md` "`@Transactional` 안의 Redis 호출" 과 같은 이유.
- **완료는 멱등**: 이미 `READY` 면 S3 를 부르지 않고 같은 응답. 동시에 두 번 오면 `markReady` 의 `WHERE status = 'PENDING'` 이 한쪽만 통과시키고 다른 쪽은 재조회
  결과를 돌려준다.
- **검증 실패 = 폐기**: 선언과 다르거나 (`HEAD` 불일치) 이미지가 아니면 (§4) **행을 먼저 소프트 삭제하고 (`PENDING` 조건) 실제로 지워졌을 때만** 객체를 지운 뒤
  `400 MEDIA_INVALID`. 0행이면 동시 완료의 다른 쪽이 그 사이 `READY` 로 바꾼 것 — 이미 게시글에 붙었을 수 있으므로 객체를 건드리지 않고 그쪽 결과를 돌려준다 (리뷰
  2026-09-20: 조건 없는 폐기는
  `READY`·첨부된 행까지 지워 게시글에서 미디어가 조용히 사라졌다). 같은 행으로 재시도할 길을 남기지 않는 이유는 presigned PUT 이 이미 만료됐을 수 있고, "다시 발급" 이 클라이언트에게 더
  단순하기 때문이다. 객체가 **아직 없으면** 폐기하지 않고 `409 MEDIA_NOT_UPLOADED` — 클라이언트가 PUT 을 마친 뒤 재호출한다.
- 기각: **서버 경유 multipart** — 서버가 바이트를 직접 보므로 검증은 쉽지만 위의 처리량 상한 문제. 이 서비스는 이미지 외에 큰 요청이 없어 업로드만 S3 직접 쓰기로 떼어내는 것이 가장 싸다.
  **완료 단계 없이 첨부 시점에 검증** — 게시글 작성 트랜잭션 안에 S3 왕복이 들어가고, 실패 시 "어느 미디어가 왜" 를 게시글 API 오류로 돌려줘야 해 계약이 복잡해진다.

### 결과

- 서버는 이미지 바이트를 **완료 시점에 헤더만** 읽는다 (§4). 업로드 대역폭은 S3 가 진다.
- 클라이언트 계약은 `README.md` "미디어 API" — URL 발급 · PUT · 완료 · 첨부 4단계.

## 2. 미디어 도메인

### 문제

미디어의 생명주기 (발급됨 → 올라옴 → 검증됨 → 게시글에 붙음)를 어디에 어떻게 기록할지, 그리고 그 각 단계가 어떤 경로에서 어떻게 실패하는지.

### 근거와 도입 방법

- `media(id, owner_id → users CASCADE, post_id → posts CASCADE, position, status, storage_key, content_type, size_bytes, width, height, created_at, ready_at, deleted_at)`.

- **상태는 둘뿐**: `PENDING`(URL 발급, 객체 유무 모름) · `READY`(완료 검증 통과). "올라왔지만 완료 안 됨" 은 상태가 아니라 `PENDING` + S3 에 객체 있음이다 — 서버는
  완료 호출 전엔 그것을 알 필요가 없다. `ck_media_ready_has_ready_at` 이 `READY ⇔ ready_at NOT NULL` 을 강제.
- **첨부는 컬럼**: 관계 테이블 없이 `media.post_id` + `position`. 미디어 하나는 게시글 하나에만 붙고 (1:N) 되돌리지 않으므로 이력 테이블이 필요 없다.
  `ck_media_attachment`
  가 `post_id IS NULL ⇔ position IS NULL` 을, `uk_media_post_position`(`(post_id, position) WHERE post_id IS NOT NULL`) 이
  같은 게시글 안 순서 충돌을 막는다.
- **객체 키** `media/{ownerId}/{uuid}.{ext}` — `uk_media_storage_key` 유니크. 소유자 접두는 버킷을 볼 때 찾기 위한 것이고 인가는 키가 아니라 `owner_id`
  로 한다.
- **소유자 검사는 404 로**: 남의 미디어 id 로 완료·첨부하면 `404 MEDIA_NOT_FOUND` — 존재 여부를 드러내지 않는다 (게시글 삭제의 403 과 다른 선택: 게시글 id 는 응답에 공개되는
  값이지만 미디어 id 는 소유자만 안다).
- **소프트 삭제**(`deleted_at`) 는 검증 실패 폐기에만 쓴다. 조회는 전부 `deleted_at IS NULL`.
- 물리 삭제: 사용자 탈퇴 `CASCADE`, 게시글 물리 삭제 `CASCADE` — 둘 다 S3 객체는 남는다 ("현재 제약과 후속 판단").

### 결과

- 상태 전이는 `PENDING → READY`(완료) · `READY, post_id NULL → READY, post_id = P`(첨부) · `PENDING → deleted_at`(폐기 — `READY` 는
  폐기하지 않는다, §1) 셋뿐이고 전부 원자 UPDATE 한 문장이다.

## 3. 게시글 첨부

### 문제

게시글 작성과 미디어 첨부를 어떻게 한 단위로 묶고, 같은 미디어를 두 게시글이 동시에 붙이려 할 때 무엇이 보장되는가.

### 근거와 도입 방법

- 작성·답글·인용 요청의 `mediaIds`(최대 `MediaPolicy.MAX_PER_POST` = 4, 중복·`null` 원소 불가 — DTO `@Size`·`@UniqueElements`·
  `@NotNullElements` 가
  `400 INVALID_REQUEST` + `fieldErrors.mediaIds`; jackson-module-kotlin 이 없어 `[null]` 이 `List<Long>` 에 그대로 들어오므로 원소
  non-null 은 커스텀 제약으로 막는다)를
  `PostService.create`/`ReplyService.reply`/`QuoteService.quote` 가 **같은 `@Transactional` 안에서**
  `MediaAttachmentService.attach` 로 붙인다. 하나라도 실패하면 예외로 게시글 INSERT 까지 롤백된다 — "게시글은 생겼는데 미디어가 일부만 붙음" 이 없다.
- **첨부는 원자 UPDATE**:
  `UPDATE media SET post_id, position WHERE id = ? AND owner_id = ? AND status = 'READY' AND post_id IS NULL AND deleted_at IS NULL`.
  조회-후-쓰기가 아니라 조건이 SQL 에 있으므로 같은 미디어를 두 게시글이 동시에 붙이면 **한쪽만 1행**이고 다른 쪽은 0행 → 그때 재조회로 이유를 분류해 `404 MEDIA_NOT_FOUND`(없음·남의
  것·폐기됨)
  / `409 MEDIA_NOT_READY` / `409 MEDIA_ALREADY_ATTACHED` 를 고른다 (분류 조회는 판정이 아니라 응답 코드 선택용 — READ COMMITTED 에서 경합에 진 쪽은 상대
  커밋 뒤 재조회하므로
  `post_id` 가 보인다). `rules/follow.md` 의 "조회 후 삽입 금지" 와 같은 원칙.
- `mediaIds` 순서 = `position` = 응답 `media[]` 순서. 다만 **UPDATE 는 id 오름차순으로 실행**한다 — 같은 소유자가 같은 미디어 둘을 역순으로 담은 게시글 두 개를 동시에
  만들면 요청 순서대로 잠그다 PG 교착 (`40P01` → 500)이 난다 (리뷰 2026-09-20). 잠금 순서만 고정하고 `position` 은 요청 순서를 유지한다.
- 의존 방향은 **`post` → `media`** 만. `media` 는 `post_id` 를 `Long` 으로만 안다.
- 기각: **게시글 작성 후 별도 첨부 API**(`PUT /api/posts/{id}/media`) — 두 요청 사이에 미디어 없는 게시글이 노출되고, 첨부 실패 시 게시글을 되돌릴 방법이 계약에 필요해진다.
  타임라인이 예정된 이상 "작성 = 완성된 게시글" 이 단순하다.

### 결과

- 게시글 응답에 `media[]` 가 실린다. 리포스트 행은 `posts` 행이지만 미디어를 갖지 않는다 (`resolveTarget` 처럼 클라이언트가 원본을 조회) — 리포스트 행 `media` 는 항상 빈
  목록.
- 첨부 실패 경로 전부가 `MediaApiTests` `첨부 검증 — …` 에 있고, 두 번째 미디어 실패 시 첫 번째 첨부 롤백도 거기서 확인한다.

## 4. 조회와 검증

### 문제

비공개 버킷의 객체를 클라이언트가 어떻게 읽고, 서버는 "올라온 것이 정말 선언한 형식의 이미지" 임을 어디까지 확인하는가.

### 근거와 도입 방법

- **읽기는 presigned GET**: 게시글 응답의 `media[].url` 은 `downloadUrlTtl`(15분) 짜리 서명 URL. 버킷은 비공개라 이 URL 밖에서는 읽히지 않는다. 기각:
  **public-read 버킷 + 고정 URL** — 삭제된 게시글의 이미지가 URL 만 알면 영구히 열리고, 버킷 자체가 공개 자산이 된다. 타임라인이 붙으면 응답당 서명 수가 늘지만 서명은 로컬 계산이라 DB
  조회보다 싸다.
- **검증은 헤더만**: 완료 시점에 `HEAD`(존재·타입·크기) → `GET` 스트림에서 `ImageProbe` 가 **매직 넘버 16바이트**로 실제 형식을 판정하고 ImageIO 리더가 있는 형식
  (jpeg·png·gif)은 헤더에서 폭·높이를 읽는다. 전체 디코딩은 하지 않는다 — 10MB 이미지도 첫 수십 바이트. 매직 넘버는 맞는데 리더가 헤더를 못 읽으면 (깨진 파일) 폐기한다. **webp 는
  JDK 에 리더가 없어** 형식만 판정하고 폭·높이는 `null` — 리더 라이브러리 추가는 후속.
- **처리는 없다**: 리사이즈·썸네일·EXIF 제거를 하지 않는다. 기각 (보류): **완료 시점 동기 썸네일** — 원본을 내려받아 디코딩해야 해 완료 API 지연이 파일 크기에 비례하고, 실패 시 폐기/재시도
  의미가 복잡해진다. 필요해지면 완료 후 비동기 (큐·S3 이벤트)로 두는 것이 맞고 그건 "다른 서비스로의 이벤트 발행 없음" 경계와 같이 개정해야 한다.

### 결과

- 저장되는 것은 선언과 일치하고 매직 넘버가 맞는 이미지뿐. `MediaVerifierTests`(HEAD 불일치·내용 불일치·webp)·`ImageProbeTests`(비이미지·깨진 헤더·webp 크기 null) 가 각각 고정한다.

## 5. 저장소 포트와 테스트

- **클래스 책임 (2026-09-20 SRP 리팩토링)**: `MediaUploadService` = 발급·완료의 상태 전이와 폐기 순서 · `MediaVerifier` = "올라온 객체가 선언한 이미지인가"
  판정 (`MediaVerdict`
  `Ready`/`NotUploaded`/`Invalid`, S3 HEAD·GET 은 여기서) · `MediaAttachmentService` = 게시글 첨부 (쓰기, 원자 UPDATE) ·
  `MediaViewService` = 게시글 응답용 조회 + presigned GET (읽기 URL 정책이 바뀌는 자리) · `S3MediaStorage`(어댑터) / `S3MediaStorageConfig`(빈
  구성, 별 파일). 게시글 쪽은 `PostTargetResolver`(대상 해석)·`PostCountsRepository`(통계 행)를 같은 이유로 분리했다.
- `MediaStorage` 인터페이스 (도메인) ↔ `S3MediaStorage`(`@Profile("!test")`, AWS SDK v2 `S3Client` + `S3Presigner`) ↔ 테스트의
  `InMemoryMediaStorage`(`TestMediaStorageConfig`).
  `rules/tests.md` 의 Redis 대체 빈과 같은 짝.
- **자격증명은 코드·설정에 없다** — SDK 기본 자격증명 체인만. 로컬은 `aws configure` 또는 env, 운영은 인스턴스 역할. 설정은 버킷·리전 (`MEDIA_S3_BUCKET`·
  `AWS_REGION`)과 TTL·크기 상한 (`sns.media.*`)뿐이며 `MediaProperties` 가 프로파일과 무관하게 바인딩된다 (테스트도 같은 상한을 본다).
- 테스트 세 층: 서비스 단위 (`MediaUploadServiceTests`·`MediaVerifierTests`·`MediaAttachmentServiceTests`·`MediaViewServiceTests`·
  `ImageProbeTests`) · API (`MediaApiTests`, PG + 인메모리 저장소 — "클라이언트가 PUT 했다" 를 `InMemoryMediaStorage.put` 으로 흉내) · **S3
  어댑터** — `S3MediaStoragePresignTests`(Docker 없음: 서명 헤더 집합·TTL). HEAD/GET/DELETE/presigned GET 왕복은 **실 S3 수동 확인** — S3
  호환 에뮬레이터 (LocalStack)는 두지 않기로 했다 (2026-09-20, 사용자 결정: 실 S3 전용). Docker 없으면 API 층은 skip.

## 현재 제약과 후속 판단

- **미디어만 있는 게시글 없음** — 본문 1~500자는 여전히 필수(`ck_posts_repost_has_no_content` 가 `content <> ''` 를 요구). 허용하려면 CHECK 를 "리포스트 행이 아니면 본문 또는
  미디어" 로 바꿔야 하는데 행 간 조건이라 CHECK 로 못 쓴다 — 앱 불변식 + 마이그레이션 개정 절이 필요.
- **정리 없음** — `PENDING` 채로 남은 행(URL 만 발급받고 안 올린 것), `READY` 인데 첨부되지 않은 것, 삭제된 게시글의 객체, 폐기 실패로 남은 객체. S3 수명 주기 규칙(`media/` 접두,
  n일) + 행 정리 배치가 후속. 주기 작업이 없다는 `00-overview.md` "타임라인" 문단도 그때 개정.
- **미디어 삭제 API 없음** · **첨부 해제 없음** · **동영상 없음** · **썸네일/리사이즈/EXIF 제거 없음**(§4) · **webp 폭·높이 없음**(§4).
- **presigned GET 만료** — 15분 뒤엔 게시글을 다시 조회해야 한다. CloudFront 서명 쿠키 등 장기 URL 은 범위 밖.
- **폐기 순서** — 검증 실패 시 행 소프트 삭제(`PENDING` 조건) 뒤 S3 `DELETE`. `DELETE` 가 실패하면 행은 이미 삭제된 채 객체만 남고 클라이언트는 `500` 을 받는다 — 재호출은
  `404 MEDIA_NOT_FOUND`(새로 발급). 객체 고아는 위 "정리 없음" 에 포함.
- **S3 어댑터의 왕복(HEAD/GET/DELETE/presigned GET)과 선언 불일치 거부는 실 S3 에서만 관측** — 에뮬레이터 없음(§5). 운영 버킷에 처음 붙일 때 발급→PUT→완료→조회 한 바퀴와
  Content-Type 을 바꾼 PUT 이 403 인지 한 번 확인한다.
- **IAM 에 `s3:ListBucket` 이 필요하다** — 없으면 S3 가 없는 키의 HEAD/GET 을 403 으로 돌려준다. `S3MediaStorage.head/open` 은 `NoSuchKey` 와 404 만 "없음" 으로 다루고 403 은
  설정 오류라 그대로 올린다(500) — README "로컬 인프라 실행" 의 권한 문단, `S3MediaStorageTests`. 수동 확인: `s3:ListBucket` 없는 역할로 업로드 전 `complete` 호출이 409 인지.
- **S3 GET 스트림은 `abort()` 로 닫는다** — SDK 의 `ResponseInputStream.close()` 는 남은 본문을 끝까지 읽어 연결을 풀에 돌려주므로 "헤더만 읽는다" 가 거짓이 된다.
  `S3MediaStorage.open` 이 `close()` 를 `abort()` 로 바꿔 연결 재사용을 포기한다(완료는 업로드당 한 번). 자동 테스트는 이 차이를 못 본다 — 수 MB 객체로 `complete` 지연이
  크기에 비례하지 않는지 한 번 수동 확인.
- **전송 오류도 폐기로 본다** — `ImageProbe.readDimensions` 의 `catch (Exception)` 은 ImageIO 헤더 파싱 실패뿐 아니라 S3 GET 스트림의 전송 `IOException` 도 `Corrupt` 로 삼아
  행·객체를 폐기한다(첫 수 KB 를 읽는 창이라 확률은 낮고, PNG 리더가 `IOException` 을 `IIOException` 으로 감싸 구분이 불완전). 전송 오류를 `NotUploaded`(재시도)로 가르는 것이 후속 선택지.
- **HEAD 와 GET 사이에 객체가 바뀔 수 있다** — 같은 presigned URL 로 다시 PUT 하면(만료 전) 내용이 바뀐다. 완료는 그 시점의 객체를 검증하며, `READY` 뒤의 덮어쓰기는 막지 못한다
  (서명 URL 만료 10분이 창). 완료 후 객체 ETag 를 저장해 조회 시 대조하는 것이 후속 선택지.
